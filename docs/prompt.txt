# FRAUDLENS — AI AGENTIC FRAUD INVESTIGATION PLATFORM

## 1. PROJECT OVERVIEW

Build a production-quality hackathon project called **FraudLens**.

### Tagline

**AI-Powered Fraud Investigation & Next-Best Action**

FraudLens is NOT a generic chatbot and NOT just a fraud detection model.

It is an **AI fraud investigator** that can:

* Investigate suspicious transactions
* Explore connected entities using TigerGraph
* Discover hidden relationships
* Retrieve similar historical fraud cases
* Analyze evidence
* Identify fraud patterns
* Assess risk and confidence
* Identify missing evidence
* Request additional evidence when necessary
* Reassess the case when new evidence arrives
* Recommend a policy-aware Next Best Action
* Handle human approval when required
* Maintain a complete investigation/case record

The core concept is:

> **Don't build “ChatGPT + TigerGraph”. Build an AI fraud investigator that can see relationships, investigate evidence, learn from previous cases, identify what evidence is missing, reconsider its assessment, and recommend a policy-aware next action.**

---

# 2. CORE AGENTIC INVESTIGATION LOOP

The most important part of the system is the autonomous investigation loop.

Implement this workflow:

```text
Suspicious Transaction / Fraud Signal
                ↓
       Create Investigation Case
                ↓
      Agent Builds Investigation Plan
                ↓
      Investigate Using TigerGraph
                ↓
      Trace Related Entities
                ↓
      Discover Hidden Connections
                ↓
       Retrieve Similar Cases
                ↓
       Analyze Evidence & Patterns
                ↓
       Assess Risk + Confidence
                ↓
       Is Evidence Sufficient?
            /          \
          NO            YES
          ↓              ↓
 Request Targeted       Continue
 Additional Evidence
          ↓
    New Evidence Arrives
          ↓
     Re-investigate
          ↓
     Reassess Risk
          ↓
      Next Best Action
          ↓
       Policy Check
          ↓
 Human Approval Required?
       /             \
     YES              NO
      ↓                ↓
 Human Approval      Execute/Simulate
      ↓                ↓
      └──────→ Case Updated
                    ↓
             Explain Decision
                    ↓
              Store Case Memory
```

The system must make this loop visible in the UI.

# 3. TIGERGRAPH INVESTIGATION

TigerGraph should be a core part of the investigation, not just a decorative graph.

The agent should use graph queries/algorithms to investigate relationships such as:

```text
Customer
   ↓
Account
   ↓
Transaction
   ↓
Device
   ↓
Other Account
   ↓
Previous Fraud Case
```

Possible entities:

* Customer
* Account
* Transaction
* Device
* Identity
* Merchant
* IP address
* Email
* Phone
* Address
* Fraud Case

Possible relationships:

* Owns
* Uses
* Transacted
* Shared Device
* Shared Identity
* Shared Contact
* Connected To
* Previously Involved In
* Reported In

The graph should help identify suspicious networks and relationships.

Do NOT create a graph that is only visual decoration.

Example:

```text

             /    |    \
           A101  A204   A331
            |      |      |
```

The investigator should be able to:

* Zoom
* Pan
* Select nodes
* Expand relationships
* Filter entity types

* Open transaction details
* Open related fraud cases
* Inspect entity information

The graph must communicate evidence and relationships.

# 5. EVIDENCE-DRIVEN AI

Every important AI conclusion must be connected to evidence.

Do NOT simply display:

> “High fraud risk.”

Instead display:

```text
HIGH RISK
88% Confidence

Supporting Evidence

✓ 3 accounts share the same device
✓ 2 connected accounts were involved in previous fraud cases
✓ Transaction pattern matches a known fraud pattern
✓ Unusual transaction velocity detected
```

Each evidence item should contain:

* Evidence type
* Source
* Related entity/transaction
* Finding
* Relevance
* Timestamp
* Confidence where applicable

The user must be able to trace:

```text
Recommendation
      ↓
Supporting Evidence
      ↓
Graph Relationship
      ↓
Underlying Entity / Transaction
```

# 6. AGENTIC RE-INVESTIGATION LOOP

This is one of the most important differentiating features.

Do NOT make the system:

```text
Detect → Score → Alert
```

Instead implement:

```text
Investigate
    ↓
Find Evidence Gap
    ↓
Request Targeted Evidence
    ↓
Receive Evidence
    ↓
Re-investigate
    ↓
Update Risk
    ↓
Make Decision
```

Example:

```text
Initial Risk
MEDIUM — 62%

        ↓

Evidence insufficient

        ↓

Agent requests customer verification

        ↓

Verification received

        ↓

Agent re-runs investigation

        ↓

Risk
HIGH — 91%

        ↓

Recommend BLOCK
```

The UI must clearly show that the assessment changed because of new evidence.

---

# 7. “WHY DID MY DECISION CHANGE?”

Implement a dedicated explanation component.

Example:

### Initial Assessment

Risk: MEDIUM
Confidence: 64%

Reason:

> Evidence was insufficient to independently confirm the suspicious account relationship.

### New Evidence

Customer verification completed.

### Updated Assessment

Risk: HIGH
Confidence: 89%

### Why did the assessment change?

The new evidence confirmed the previously uncertain relationship.

This demonstrates that the agent is dynamic and evidence-driven rather than a static classifier.

# 8. FRAUD CASE MEMORY

Implement historical case memory.

The agent should retrieve similar previous investigations and use them during the current investigation.

Example:

> “This case resembles 7 previously investigated cases.”

Display:

```text
Current Case
     ↓
Similar Historical Cases
     ↓
Common Entities
     ↓
Common Fraud Pattern
     ↓
Previous Analyst Decisions
     ↓
Previous Actions / Outcomes
     ↓
Current Recommendation
```

Similar case cards should show:

* Case ID
* Similarity reason
* Fraud pattern
* Previous decision
* Action taken
* Outcome
* Relevant entities

The agent should not treat every investigation as completely new.

---

# 9. POLICY-AWARE NEXT BEST ACTION

The agent must not simply output:

> BLOCK ACCOUNT

Instead create a structured recommendation:

```text
NEXT BEST ACTION

BLOCK ACCOUNT

Reason
Multiple connected suspicious entities.

Supporting Evidence
✓ Shared device
✓ Previous fraud case
✓ Abnormal transaction pattern

Policy
Account blocking requires analyst approval.

Approval
⚠ HUMAN APPROVAL REQUIRED
```

Possible actions:

* Allow transaction
* Block transaction
* Monitor account
* Block account
* Warn customer
* Create/escalate case
* Request more evidence
* File report
* Close case

The system should distinguish between:

**Agent recommendation**

and

**Human authorization**

---

# 10. HUMAN APPROVAL

For actions requiring approval, create a proper approval interface.

Display:

* Recommended action
* Reason
* Supporting evidence
* Relevant policy
* Potential impact
* Approval requirement

Actions:

```text
[ APPROVE ]
[ REJECT ]
[ REQUEST MORE EVIDENCE ]
```

For the hackathon, actions can be simulated/stubbed if real banking APIs are unavailable.

# 16. EXPLAINABILITY

The final case summary must answer:

1. What triggered the investigation?
2. What did the agent investigate?
3. What graph relationships were discovered?
4. What evidence supports the findings?
5. What fraud pattern was identified?
6. What is the risk?
7. What is the confidence?
8. Why was additional evidence requested?
9. What changed after new evidence?
10. What Next Best Action is recommended?
11. Why is the action recommended?
12. Is human approval required?
13. What policy applies?
14. What was the final outcome?

Do not expose raw chain-of-thought. Provide concise evidence-based explanations.

# 20. FINAL PRODUCT DEFINITION

FraudLens is:

> **An AI agentic fraud investigation platform that uses TigerGraph to understand relationships between transactions, accounts, devices and other entities; combines graph evidence with historical case memory and fraud policies; identifies evidence gaps; requests targeted evidence; dynamically reassesses risk; and produces an explainable, policy-aware Next Best Action with human approval when required.**

Build the project around this concept.

Prioritize:

1. Working end-to-end investigation loop
2. TigerGraph integration
3. Evidence-driven reasoning
4. Agentic re-investigation
5. Case memory
6. Policy-aware Next Best Action
7. Human approval
8. Explainability
9. Premium investigation UI
10. Strong 3–5 minute demo experience

Do not add random features just to increase feature count.

Every feature should strengthen the core investigation loop.
